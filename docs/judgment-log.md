# Judgment log – P1 Registry API

Format per entry: AI suggested / I decided / Why / Research (optional).

## Foundations (steps 1–3)

### 1. Database access
- **AI suggested:** stdlib sqlite3 as the spec says; Alon mentioned MySQL may come later via an env var.
- **I decided:** stdlib sqlite3, no ORM. All DB code lives only in db.py.
- **Why:** follow the spec now; a later switch to MySQL touches one file.

### 2. Foreign keys
- **AI suggested:** PRAGMA foreign_keys = ON.
- **I decided:** enable it on every connection.
- **Why:** SQLite does not enforce foreign keys by default.

### 3. Connections
- **AI suggested:** a new connection per request via a FastAPI dependency.
- **I decided:** get_db() with yield/finally, so the connection is always closed.
- **Why:** safe for concurrency and fast enough; a pool later only changes db.py.

### 4. registry.db in git
- **I decided:** registry.db is git-ignored; seed_registry.sh is committed.
- **Why:** the data is generated by the script; the script is the source of truth.

### 5. 422 detail text
- **AI suggested:** a generic "Request validation failed".
- **I decided:** detail = "field: message; ..." for every failing field.
- **Why:** the client needs to know exactly what to fix.

### 6. Error code for 405
- **AI suggested:** no code (the spec lists none for 405).
- **I decided:** 405 returns code VALIDATION.
- **Why:** the client sent a request the API does not accept; that is a client error.

### 7. Response models
- **I decided:** Pydantic response models in models.py.
- **Why:** guarantees only the listed fields are returned, and Swagger shows the schemas.

### 8. No Factory pattern for catalogues
- **AI suggested:** (considered) a Factory per crop type.
- **I decided:** no Factory.
- **Why:** crops differ only in data, not behaviour. Adding a crop = a DB row, not new code.

### 9. SQL helpers
- **AI suggested:** two generic helpers in db.py (list_rows, get_row), table names in main.py.
- **I decided:** accepted.
- **Why:** keeps all SQL in one module, matching decision 1.

## Step 4 – Farms CRUD (FR-1.1)

### 10. Who generates the farm id
- **AI suggested:** the server, with uuid4.
- **I decided:** the server generates str(uuid.uuid4()); the client sends only "name".
- **Why:** the side that stores the data owns the ids; avoids collisions and extra validation. The seed already uses UUIDs, so all ids share one format.
- **Research:** checked the seed with sqlite3 — existing farm ids are UUIDs.

### 11. PATCH with an empty body {}
- **AI suggested:** 422.
- **I decided:** 422 VALIDATION "no fields to update"; null or "" name -> 422.
- **Why:** an empty update is almost certainly a client mistake; better to say so than silently do nothing.

### 12. Duplicate farm name
- **AI suggested:** allow it (the spec only requires unique plot names; the farms table has no UNIQUE on name).
- **I decided:** block it -> 409 CONFLICT on POST and PATCH (renaming to its own name is allowed).
- **Why:** a farm name works like a company name; two farms with the same name would confuse users. This rule is beyond the spec, on purpose.
- **Note:** checked in code, not by a DB constraint, because the schema comes from seed_registry.sh and is not changed.

### 13. Deleting a farm that still has plots
- **AI suggested:** count plots first; keep the FK as a safety net.
- **I decided:** count first -> 409 CONFLICT "farm has N plots".
- **Why:** a clear message for the client; SQLite's FK error is generic.

## Step 5 – Plots CRUD + validations (FR-1.1, FR-1.3)

### 14. Unknown farm_id in the request body
- **AI suggested:** 422 (404 is for the id in the URL).
- **I decided:** 422 VALIDATION.
- **Why:** consistent with crop_id/soil_id/emitter_id, which the spec already sends to 422. 404 only when the id in the URL does not exist.

### 15. May PATCH move a plot to another farm?
- **AI suggested:** allow it.
- **I decided:** allow it (I first chose to block it, then changed my mind).
- **Why:** the plot's own id never changes, but farm_id is only a reference (like an address on an ID card). A single plot can be sold to a neighbouring farm. Moving re-checks that the new farm exists (422) and the name is unique there (409).

### 16. "Planting date not in the future" – whose "today"?
- **AI suggested:** UTC + one day of tolerance.
- **I decided:** the local date at the plot's location: timezonefinder(lat, lon) -> zone -> today there. Fallback UTC.
- **Why:** each farmer can record up to their own today — no false rejections and no "tomorrow" slipping through.
- **Research:** planting/transplanting is recommended early morning or late afternoon/evening, never around midnight. But what matters is when the date is entered, not when planting happens. Plain UTC fails east of UTC: a farmer in Japan (UTC+9) entering today's date at 07:00 local is still "yesterday" in UTC and would be rejected. The furthest zone is UTC+14 (Kiribati). Options compared: plain UTC, server clock, UTC + 1 day, longitude/15 approximation, timezonefinder library.

### 17. Unknown fields in the body
- **AI suggested:** extra="forbid".
- **I decided:** all request models (farms and plots) reject unknown fields -> 422.
- **Why:** a typo like "nmae" in a PATCH would otherwise return 200 and change nothing. Real cases: developer typos, clients sending the whole object back (including id), old app versions.

### 18. Duplicate plot name in the same farm
- **AI suggested:** check in code AND catch the UNIQUE IntegrityError.
- **I decided:** both -> 409 CONFLICT "plot name already exists in this farm".
- **Why:** the check gives a clear message; the DB constraint covers two simultaneous requests.

### 19. GET /v1/plots?farm_id=<unknown farm>
- **AI suggested:** return an empty list (it is a filter).
- **I decided:** 404 NOT_FOUND "Farm not found".
- **Why:** the client should know the farm does not exist, not think it simply has no plots.

### 20. Check order deviation (accepted)
- **AI reported:** FastAPI parses the body before the handler, so PATCH to an unknown plot with a malformed body returns 422, not 404.
- **I decided:** accept it.
- **Why:** rare edge case; fixing it means bypassing FastAPI's validation.

## Step 6 – 503 UNAVAILABLE (FR-1.4)

### 21. Retry-After value
- **AI suggested:** 5 seconds.
- **I decided:** 30 seconds (`Retry-After: 30`).
- **Why:** sqlite3 waits 5s on a lock (now explicit: `timeout=5`), so every 503 here is a long outage, not a blip.
- **Research:** no single standard. Examples found: 1s (DB unavailable in an open-source project), 30s (overload), 60s (dependency/DB failure), 300s (maintenance). Retry-After is a minimum; good clients add exponential backoff with jitter so they don't all retry at once.

### 22. Which errors become 503
- **AI suggested:** only "can't open" and "locked/busy"; other OperationalErrors are bugs -> 500.
- **I decided:** same, matched by SQLite error code (`sqlite_errorname`), not by message text.
- **Why:** 503 means temporary; a bug never fixes itself by retrying, and retrying would hide it. Error codes are stable; message wording can change between SQLite versions.
- **Research:** the sources said a wrong schema is a 500 and a restarting DB is a 503.

### 23. /health checks the DB
- **AI suggested:** `SELECT 1`; 503 + Retry-After on failure.
- **I decided:** yes.
- **Why:** a health check that always says 200 lies to monitoring when the DB is down; also makes FR-1.4 easy to demo.
- **Research:** the sources showed health endpoints returning 503 + Retry-After when a dependency fails.

### 24. What /health checks
- **AI reported:** `SELECT 1` never touches a table, so /health stayed 200 while the DB was locked.
- **I decided:** `SELECT 1 FROM farms LIMIT 1`.
- **Why:** /health should answer "can the service work with its data", not just "can it open a connection". It now catches a missing file, a lock and missing tables. Cost: during a lock /health waits up to 5s before answering; acceptable, since it only happens when something is really wrong. LIMIT 1 keeps it fast.

## Step 7 – Tests

### 25. Test DB isolation
- **AI suggested:** three options: the real DB, one shared test DB, or a fresh DB per test.
- **I decided:** a fresh DB per test, built from a template (the seed is built once per session, then copied per test). Patch `db.DB_PATH` instead of overriding `get_db`.
- **Why:** full isolation and fast. Patching DB_PATH keeps the real get_db (mode=rw, timeout=5, foreign_keys) in the tests; overriding get_db would skip it.
- **Research:** the consensus is no shared state between tests; shared DB state causes flaky tests that pass alone and fail together. Common methods: transaction rollback (fastest in general; one source measured ~5s vs ~60s for 100 tests compared with recreating the schema), truncating tables, or a new DB per test (cheap with SQLite, a file copy). Rollback does not fit here: db.py commits on every write, and the 503 test needs a missing file. Real SQLite projects use "build a template once, copy per test" (Microsoft PyRIT; codeframe measured ~1.3s to build vs ~0.1ms to copy; pytest-postgresql and pytest-mock-resources use template databases too). FastAPI's docs recommend dependency_overrides on get_db.

### 26. Test scope
- **Research:** error paths matter as much as happy paths; check the body and headers, not only status codes; a second DELETE should return 404, not 500; a 500 on bad input is a bug; test the contract, not the implementation.
- **I decided:** cover every case in the explicit list (the Postman cases plus a few more), and every judgment-log decision gets a test that proves it. Not every possible edge case: the task asks for a small model.

### 27. Controlling time in tests
- **Problem:** a fixed future date (e.g. 2027-01-01) becomes a past date in 2027 and the test breaks. The Japan case can only be tested by controlling the clock.
- **Research:** freezegun is the older library and has a long-open bug around time zones; a user in that issue recommended time-machine as faster and more solid. time-machine supports ZoneInfo time zones and ships a pytest plugin.
- **I decided:** time-machine with tick=True, and every test runs at 2026-11-03 22:00 UTC.
- **Why:** it proves decision 16: at 22:00 UTC a farmer in Tokyo (already Nov 4) is accepted, while London (still Nov 3) is rejected. tick=True keeps the clock moving so TestClient's internal timers never freeze.

### 28. Locked-DB test skipped
- **Why:** it needs a real 5s wait; the lock -> 503 path was verified manually in step 6.

### 29. Test safety
- **I decided:** the seed script is copied and run in a temp dir, never in place, and the real registry.db mtime is checked before and after the run.
- **Why:** running it in place could overwrite the real DB.
- **Result:** mtime unchanged.

### 30. Self-review of the test prompt
- **I decided:** reviewed the prompt twice before sending it.
- **Round 1 found:** Claude Code cannot see Postman (so I gave an explicit case list); a risk that the seed script overwrites the real DB; a possible DB_PATH import-time trap; a fully frozen clock could hang TestClient (so tick=True); pytest needed pythonpath.
- **Round 2 found:** 4 missing cases (PATCH null, empty plot name, PATCH unknown plot, PATCH unknown farm).
- **Why:** catching these before running is cheaper than debugging after.

### 31. httpx -> httpx2 for the TestClient
- **Problem:** the first run passed (63 tests) but showed StarletteDeprecationWarning: using httpx with starlette.testclient is deprecated, install httpx2.
- **Research:** Starlette 1.2.0 (May 2026) moved its TestClient to httpx2. The old path still works with a warning, but becomes a hard error if warnings are escalated, and will be removed. Other projects fixed it the same way: add httpx2 to the test dependencies.
- **I decided:** uv remove --dev httpx; uv add --dev httpx2. No code change: Starlette picks httpx2 automatically.
- **Result:** 63 passed, no warnings.

## Step 8 – Performance (NFR-1.1)

### 32. Load-test tool
- **Research:** most simple load tools wait for each response before sending the next ("closed model"). When the server stalls they stop sending, so slow periods are under-sampled and p95/p99 look better than reality. This is called coordinated omission (term from Gil Tene). The fix is an "open model": send at a fixed arrival rate regardless of responses, which is exactly what "at 10 rps" means. One published comparison of the same slowdown measured p95 67 ms with a closed model vs 1 s with an open model.
- **Tools:** k6 (constant-arrival-rate executor = open model, built-in pass/fail thresholds, most documented). Vegeta (constant-rate CLI, simpler, no thresholds). Locust (usually recommended for Python teams, but has no arrival-rate mode, so it is the wrong fit for "at 10 rps"). wrk (last commit Dec 2023, closed model).
- **AI suggested:** k6.
- **I decided:** k6, installed system-wide via the official apt repo.
- **Why:** it measures exactly what the requirement says, turns NFR-1.1 into an automatic pass/fail check, and it's a tool I'll keep using after the course.

### 33. Duration and warm-up
- **Research:** Grafana's k6 guide says baseline data comes from the steady-state stage and it should last at least 1 minute so metrics reflect consistent behaviour, not warm-up effects. Several sources recommend a short warm-up before measuring (caches, connections, startup). A Kafka benchmark discussion explained that a short run reports a worse p99 than a long run of the same system, only because startup latency pollutes it. 15–20+ minutes is suggested for heavy load tests, which is overkill for a local 10 rps target.
- **AI suggested:** 10 s warm-up (not measured, separate scenario) + 2 min measured.
- **I decided:** same.
- **Why:** the first requests load Python modules, which is not normal work. 2 min = 1,200 samples per endpoint, double k6's minimum.

### 34. Which endpoints, and "10 rps" per endpoint or total
- **Research:** the requirement is ambiguous. k6 can set thresholds per tag/scenario, so a slow endpoint can't hide behind an average of all endpoints.
- **Options:** 10 rps total spread over 4 endpoints (~2.5 rps each, too lenient); 10 rps each for farms/plots list + by-id in parallel (40 rps); or all 10 GET endpoints (100 rps; catalogues use the same list_rows/get_row helpers).
- **AI suggested:** 10 rps per endpoint for the 4 farm/plot endpoints, in parallel.
- **I decided:** same.
- **Why:** the stricter reading. If each endpoint meets 100 ms while all run together, it surely meets it at 10 rps alone.
- **Open question for Alon:** which reading did Alon intend?

### 35. dropped_iterations must be 0
- **Research:** with an arrival-rate executor, if k6 can't start an iteration on time it drops it. The reported percentiles then exclude the dropped requests.
- **I decided:** a threshold `dropped_iterations count==0` per scenario, verified first with a throwaway script (one arrival-rate scenario, empty iteration, no HTTP).
- **Result:** the threshold passed (`✓ 'count==0' count=0`). k6 reports the counter as 0 for the scenario, so an empty sub-metric is not a threshold error.
- **Why:** otherwise a "passing" p95 could be missing exactly the slowest moments.

### 36. Measurement limits
- **Limit:** k6 and the server run on the same laptop (WSL2), with one uvicorn worker and SQLite. Results show the service meets the target locally; they are not a production capacity number.
- **Output:** the raw output is saved to `perf/results.txt` (run with `--quiet`, so it holds only the summary) for the PR. `tee` hides k6's exit code, so pass/fail is read from the ✓/✗ marks. That is fine for a manual run; CI would need `pipefail`.

### 37. Self-review of the step 8 prompt (3 rounds)
- **Round 1 found:** a threshold on a metric with no samples might error; the result must be saved for the PR (tee); the same-machine limitation must be stated; one research claim was worded stronger than its source.
- **Round 2 found:** the prompt asked to verify k6's behaviour while forbidding any k6 run (fixed with a throwaway script with no HTTP); the progress bar would flood results.txt (fixed with `--quiet`).
- **Round 3 found:** the throwaway script didn't specify the arrival-rate executor (dropped_iterations exists only there), and a sleep could cause real drops. Fixed by specifying the executor and an empty iteration.
- **Why:** each round found fewer problems. The remaining check was running it (done in decision 35).

### 38. Bug found by the load test: SQLite thread check
- **Problem:** 73% of requests failed at 40 rps (3,597 of 4,903) with "SQLite objects created in a thread can only be used in that same thread" (main.py get_db -> conn.close()). Postman and the 63 tests missed it because they send one request at a time, so the same thread usually handles the whole request.
- **Research:** FastAPI's official docs explain that SQLite by default lets only one thread talk to a connection, to prevent sharing one connection across different requests, but with normal def functions FastAPI can use more than one thread for the SAME request, so check_same_thread=False is needed. A FastAPI GitHub issue reports deadlocks when a dependency is combined with a small connection pool.
- **Options:** check_same_thread=False (one line, the official recommendation); open/close the connection inside every endpoint (breaks decisions 3 and 6); make everything async (sqlite3 is blocking, one slow query would stall the whole server).
- **AI suggested:** check_same_thread=False.
- **I decided:** same.
- **Why:** decision 3 gives a new connection per request, so a connection is never shared between requests; it only moves between threads inside one request, exactly the case the docs describe. The pool deadlock is not relevant now (no pool), but must be checked if we move to MySQL with a pool.

### 39. Concurrency regression test
- **Lesson:** the tests only sent one request at a time.
- **I decided:** tests/test_concurrency.py fires 240 requests from 20 threads through one shared TestClient, using a `with TestClient(app)` block (one long-lived event loop and threadpool, like uvicorn). It counts both non-200 responses and raised exceptions, written red -> green: it was confirmed to FAIL before the fix and PASS after it.
- **Why:** a test that passes before the fix proves nothing; this one guards against the bug coming back.

### 40. Self-review of the bug-fix prompt
- **Found:** TestClient re-raises server exceptions by default, so the test must count exceptions as failures (not only non-200); and all threads must share ONE TestClient, otherwise there may be no real concurrency.
- **Why:** without these, the red step could fail for the wrong reason or not reproduce the bug at all.

### 41. First attempt at the regression test did not reproduce the bug
- **AI reported:** 240 and then 1000 concurrent requests through a bare `TestClient(app)` passed with 0 failures, so it stopped before fixing instead of claiming the bug was reproduced.
- **Cause (hypothesis, then tested):** a bare TestClient gives each request its own short-lived event loop and threadpool, so the dependency and the endpoint run on the same thread; uvicorn has one long-lived loop and a shared pool.
- **I decided:** use `with TestClient(app)` for this test only (one long-lived loop). Fallback if that also failed: a test against a real uvicorn.
- **Result:** before the fix, 238 of 240 requests failed (all `ProgrammingError`, 2 returned 200). After the fix, the full suite passes (64 tests).
- **Why:** a regression test is only useful if it is proven to fail without the fix.
